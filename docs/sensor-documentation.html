1 · Shared sensor architecture

All five sensors follow the same pattern: they are mounted to the ego-truck body frame, read the world state (scene geometry, machine list, or truck kinematics), apply a measurement model with noise, and publish into a 2D instrument panel (plus, for camera/LiDAR, directly into the 3D view). This mirrors how a real autonomy stack treats sensors as independent nodes publishing on their own clocks.

1.2 Render-layer separation

Three render layers keep the sensors honest:

  • Layer 0 — physical world. Terrain, machines, piles. Every camera sees it.
  • Layer 1 — debug/UI overlays. Machine labels, LiDAR point cloud, sensor gizmos, camera frustum helper, radar FOV wedge. Enabled only on the viewer camera — the sensor camera cannot see its own debug artifacts, so the RGB feed stays physically plausible.
  • Layer 2 — raycast colliders. Invisible oriented boxes (one per machine) + ground + rocks + stockpile cone. The LiDAR raycaster is restricted to this layer via raycaster.layers.set(2), trading visual fidelity for a ~40× cheaper raycast set (~100 primitives vs. thousands of triangles).

1.3 Rig configuration (inputs common to camera / LiDAR / radar)

The left-panel sliders write into a single rig object; applyRig() pushes it to the mounts every change. Defaults (DEFAULT_RIG, src/sensors.js):

camera: { x: 0, y: 7.6, z: 5.8, pitch: -6°, yaw: 0°, fov: 70° }
lidar:  { x: 0, y: 8.4, z: 1.0, yaw: 0°, range: 120 m }
radar:  { x: 0, y: 3.2, z: 6.4, pitch: 0°, yaw: 0°, range: 150 m, fov: 90° }

Positions are meters in the truck frame (y = height above ground, z = forward of body center); rotations are applied to the mount Object3D so children (sensor + gizmo) move together.

1.4 Noise model

All stochastic terms use a cheap approximate Gaussian (sum of 4 uniforms, Irwin–Hall):

const gauss = () => (Math.random()+Math.random()+Math.random()+Math.random() - 2) / 2;  // ≈ N(0, 0.29)

Biases (IMU) are drawn once at construction — constant per run, like a real un-calibrated sensor.

CAMERA2 · Camera — RGB feed + object detection

2.1 What it is

A forward-looking RGB camera on the cab roof. Unlike the other sensors it is not an analytic model: it is a real second render of the same 3D scene from a pinhole THREE.PerspectiveCamera, so occlusion, perspective, lighting and shadows in the feed are exact. On top of the feed a detector draws YOLO-style 2D boxes.

2.3 Implementation

Feed. The camera is a child of a mount Object3D on the truck. Because three.js cameras look down −Z but the truck's forward is +Z, the camera is flipped with camera.rotation.y = Math.PI. Each frame the panel's getBoundingClientRect() is converted to a GL viewport (y = windowHeight − rect.bottom; three multiplies by pixel ratio internally) and the scene is rendered again inside a scissor. The camera's layer mask is {0} so labels, the LiDAR cloud and gizmos are invisible to it.

Detector. There is no neural net — the simulator has ground truth, so it emulates a detector's output contract: for each machine the 8 corners of its oriented bounding box (from dims + yaw) are transformed into camera space; corners with z > −0.5 (behind the near region) are discarded; the rest are projected to NDC and min/max-ed into a 2D box, clipped to the image. Confidence decays with range and gets ±2% jitter:

conf = clamp(1.04 − dist/340 + N(0, 0.02), 0.28, 0.99)   // drops below threshold ≈ 320 m

2.5 Where to see the output

  • CAMERA panel (top right): live RGB feed with green/colored detection boxes — class confidence% range per target, crosshair reticle, REC tag.
  • HUD → DETECTIONS: current detection count.
  • 3D view: cyan camera gizmo + wireframe frustum (toggle "Sensor gizmos").
  • Panel meta shows configured FOV and detection count.

2.6 Design considerations

  • Same scene, second pass — not a second scene. A three.js scene cannot be shared across WebGL contexts, so the feed uses viewport/scissor on the one renderer rather than a second <canvas> + renderer. This also halves GPU memory.
  • Layer hygiene. Forgetting to move overlays to layer 1 makes the "camera" see its own LiDAR points — a classic sim-fidelity bug.
  • Aspect & DPI. The projection aspect must track the panel's CSS rect, and viewport math must not double-multiply by devicePixelRatio (three already does).
  • Detector realism knobs. Range-based confidence + jitter approximates real detector behavior; to be harsher, add occlusion checks (raycast to target center) and truncation-based confidence reduction.

2.7 Real-stack mapping

The feed is what you would pipe into YOLO / Detectron2; the overlay reproduces their output format (class, score, xyxy box). OpenCV would sit between them for undistortion — the pinhole model here is distortion-free, so that stage is an identity.

LIDAR3 · LiDAR — rotating multi-channel scanner

3.1 What it is

A 32-channel mechanical spinning LiDAR (Velodyne/Ouster class) on a mast above the cab. It produces a genuine point cloud by raycasting — every point is a real geometric intersection with the scene, so shadows/occlusion behave correctly.

3.3 Implementation

Per frame the scanner advances its azimuth by 45° in 3° steps; for each step it fires all 32 channels (elevations linearly spaced −22°…+8°). Direction in world space:

az = truckYaw + mountYaw + azimuth
dir = ( sin(az)·cos(el),  sin(el),  cos(az)·cos(el) )
raycaster.set(mountWorldPos, dir);  raycaster.far = range;
hits = raycaster.intersectObjects(colliders);          // layer-2 proxies only

A hit writes into a fixed-size ring buffer (maxPoints = 32 × 120 = 3840 — exactly one revolution): world position (±0.4% multiplicative range noise) into the THREE.Points geometry, HSL color by height (blue→red) brightened by intensity, and an ego-frame copy (world delta rotated by −truckYaw) for the BEV panel. Misses park the point at y = −1000 and mark it invalid. 480 rays/frame ≈ 28,800 rays/s.

Intensity comes from the collider's userData.intensity: machines 0.95 (metal), stockpile 0.45, rocks 0.35, ground 0.25 — enough for the BEV panel to make obstacles pop while ground returns stay dim.

3.5 Where to see the output

  • 3D world view: the live point cloud (toggle "LiDAR cloud in 3D"), colored by height — you can watch the sweep paint machines as the truck drives past.
  • LIDAR — BEV panel: ego-centric top-down plot, 30 m range rings, ego triangle, ground returns dimmed, obstacle returns bright.
  • Panel meta: valid point count and estimated revolution rate (≈7.5 Hz).
  • Green puck gizmo on the mast shows the mount.

3.6 Design considerations

  • Budget the rays. rays/frame = channels × (sweep°/step°). 480 vs ~100 colliders is real-time; raycasting visual meshes instead would not be. Collider proxies are the single most important performance decision.
  • Sector-per-frame scanning (not full 360° each frame) reproduces the rolling-shutter nature of spinning LiDAR — a fast-moving ego smears the cloud exactly like real logs do.
  • Ring buffer sizing: exactly one revolution means old points are overwritten by the returning sweep — no unbounded growth, no manual cleanup.
  • Vertical FOV asymmetry (−22°/+8°) matches truck-roof mounting: most information is below the horizon; raising the mast height slider visibly pushes the first ground ring outward.
  • Noise multiplicative on range, not additive on position — far returns get proportionally noisier, like real time-of-flight jitter.

3.7 Real-stack mapping

The ring buffer is a sensor_msgs/PointCloud2 (xyz + intensity). The BEV panel is the representation BEVFusion / PointPillars rasterize before detection; PCL/Open3D would consume the same buffer for ground segmentation (here trivially separable via intensity/height).

RADAR4 · Radar — FMCW-style cone scan

4.1 What it is

A front-bumper 77 GHz-class radar. Radar is modeled analytically (no raycasts): it outputs an object/track list — range, bearing, radial velocity, RCS — which is what automotive radars actually publish after on-chip processing. It is also the sensor the truck's AEB uses.

4.3 Implementation

Every 1/15 s the sensor iterates the machine list. For each target within range and FOV it emits a track:

range   = |Δxz| + N(0, 0.35 m)
bearing = wrap(atan2(Δx, Δz) − (truckYaw + mountYaw)) + N(0, 0.006 rad)
vr      = −(v⃗ego · LOS) + N(0, 0.12 m/s)     // targets are static ⇒ ego motion only
rcs     = 10·log10(w·h·l) + N(0, 1.5) dBsm    // size proxy

Because targets are stationary, closing speed is entirely ego-induced: driving toward a machine gives positive vr (closing), which the PPI colors red vs. orange. With 6% probability per scan a clutter ghost (random range/bearing, low RCS) is injected so downstream logic can't assume a clean sensor. nearestAhead() feeds the truck's AEB: any non-clutter track inside ±12° of boresight closer than 45 m linearly caps the speed target, reaching 0 at 12 m.

4.5 Where to see the output

  • RADAR — PPI panel: wedge-shaped plan-position indicator with 3 range rings, animated sweep line, blips (red = closing, orange = static/opening, gray = clutter), and per-track range / vr labels; dashed boresight.
  • 3D view: translucent red FOV wedge on the bumper (toggle "Sensor gizmos").
  • Behavior: park a machine on the road (or yaw the radar) and watch SPEED drop — AEB in action.
  • Panel meta: track count + configured range.

4.6 Design considerations

  • Model the output contract, not the physics. Simulating chirps/FFTs is wasted effort for autonomy logic; what matters downstream is the track list schema and its failure modes (angular blur, clutter, no classification).
  • Angular noise ≫ range noise (0.34° vs 0.35 m) — radar's real weakness. At 150 m a blip wanders ~1 m laterally, which is why radar alone can't lane-assign.
  • Radial velocity is the payoff — it's instantaneous and Doppler-accurate; the AEB keys on geometry + range but a better implementation would gate on vr > 0 (closing only).
  • Clutter injection forces consumers to be robust; the AEB filters it by class here, a real system would use track persistence (M-of-N confirmation).
  • Sweep line is cosmetic — the scan is instantaneous each update; the animation conveys the 15 Hz cadence.

4.7 Real-stack mapping

Equivalent to a Continental ARS548 / Bosch corner-radar object list on CAN/Ethernet, or a radar_msgs/RadarTrack array in ROS 2. The AEB coupling reproduces the classic radar-driven longitudinal safety channel.

IMU5 · IMU — 6-DOF inertial measurement

5.1 What it is

A cab-mounted MEMS IMU: 3-axis accelerometer + 3-axis gyroscope (+ derived roll/pitch/yaw). It is generated from the truck's kinematic state — the same signals a real IMU would sense — then corrupted with bias, white noise, and speed-dependent vibration.

5.2 Architecture & flow

Strip chartsax · az · gyro-y

5.3 Implementation

vib     = min(1, v/8) · 0.35                       // engine/road vibration grows with speed
accel.z = dv/dt        + bias_az + N(0,.05) + N(0,vib)   // longitudinal (braking spikes negative)
accel.x = v·yawRate    + bias_ax + N(0,.05) + N(0,vib)   // lateral (turns)
accel.y = 9.81         + N(0,.08) + N(0,1.6·vib)          // gravity + road chatter
gyro.y  = yawRate      + bias_gy + N(0,.004)              // yaw rate — the navigation-critical axis
gyro.x/z = N(0,.006·(1+vib))                              // roll/pitch rates ≈ 0 on flat terrain

Biases are sampled once in the constructor (σ ≈ 0.02 m/s², 0.001 rad/s) — restarting the sim gives a differently mis-calibrated IMU. Each update pushes into 260-sample history arrays that the strip-chart panel renders directly.

5.4 Inputs

InputSourceEffect

The IMU has no rig sliders — it is body-fixed at the cab. Adding a lever-arm offset (a·= a + ω̇×r + ω×(ω×r)) is a good extension exercise.

5.5 Where to see the output

  • IMU — 6-DOF panel: three scrolling strip charts — lateral accel (violet), longitudinal accel (cyan), yaw rate (yellow) — with live numeric values.
  • Recognizable signatures: departure = cyan step up; braking at B = cyan step down; each S-curve = paired violet + yellow lobes; standing at load = flat biased lines with small noise.
  • Panel meta: |a| horizontal magnitude.

5.6 Design considerations

  • Derive from the integrator, don't differentiate rendered positions — finite-differencing rendered transforms amplifies frame jitter into garbage accelerations. The truck exposes accelLong/yawRate analytically.
  • Centripetal term matters: a_lat = v·ω is what makes the IMU "feel" turns even at constant speed — the signature an EKF uses to constrain heading.
  • Bias vs noise separation is the whole point of IMU modeling: noise averages out, bias does not — it's why raw IMU integration drifts and needs GPS fusion.
  • Speed-scaled vibration reproduces haul-truck reality (engine + road) and gives the charts an honest texture instead of clean textbook lines.

5.7 Real-stack mapping

Publishes what sensor_msgs/Imu carries (linear_acceleration, angular_velocity, orientation). Fusing this 200 Hz stream with the 5 Hz GNSS below is the canonical robot_localization EKF exercise.

GNSS6 · GNSS / RTK — geodetic positioning

6.1 What it is

An RTK-corrected GNSS receiver (mining fleets run base-station RTK for cm-level positioning). It converts the truck's world position (local ENU meters) into WGS-84 latitude/longitude around a Pilbara-like site origin, at 5 Hz with centimeter noise, plus the standard NMEA-style health fields.

6.3 Implementation

east  = x + N(0, 0.03);   north = −z + N(0, 0.03)          // 3 cm RTK-fixed noise
lat   = −23.3582 + north / 111320
lon   = 119.7521 + east  / (111320 · cos(lat₀))

hdop  = 0.5 + |N|·0.15;   sats = 13…16;   mode = "RTK-FIX"

Each epoch also appends the true position to a 1200-point breadcrumb ring used by the mini-map. The equirectangular small-area approximation is exact enough for a ±500 m site (error ≪ noise).

6.5 Where to see the output

  • GNSS / RTK panel readout: mode, satellites, LAT/LON (6 decimals ≈ 11 cm), ALT, VEL, COG, HDOP, and raw ENU meters.
  • Mini-map: dashed yellow planned path, green A / orange B, cyan breadcrumb trail (grows every trip), ego arrow with heading.
  • HUD → HEADING is the same compass convention (0° = north, clockwise).

6.6 Design considerations

  • Get the frame conventions right once: three.js is Y-up with −Z as "north" here; COG must be atan2(east, north), not raw yaw — the difference is a classic source of 180°-flipped headings.
  • Noise belongs in ENU meters, then converts — adding noise in degrees makes it latitude-dependent and unit-opaque.
  • Epoch-based updates (accumulator, 5 Hz) rather than per-frame — downstream consumers must handle a position that is always slightly stale, exactly like real GNSS.
  • Honest metadata: HDOP/sats/mode let you script degradation scenarios (e.g. mode="FLOAT", σ=0.5 m in a simulated pit-wall shadow) without touching consumers.

6.7 Real-stack mapping

sensor_msgs/NavSatFix + COG/SOG from an NMEA VTG sentence. The ENU↔geodetic conversion is what geodesy/proj do around a datum; the breadcrumb-vs-planned-path map is a minimal fleet-management view (MineStar-style).

8 · Extending the sensors

  • Camera: occlusion-aware confidence (raycast to target), lens distortion via post shader, a second rear camera (another mount + scissor rect).
  • LiDAR: dual returns, beam divergence with range, per-channel dropout, PCD/PointCloud2 export of the ring buffer.
  • Radar: track persistence + M-of-N confirmation, multipath ghosts near large machines, closing-velocity-gated AEB.
  • IMU: lever-arm compensation, bias random-walk (temperature drift), quaternion orientation output.
  • GNSS: RTK→FLOAT degradation zones, multipath near high walls, separate heading-from-dual-antenna.
  • Fusion: a 15-state EKF consuming IMU @ high rate + GNSS @ 5 Hz, with the pure-pursuit tracker consuming the estimate instead of ground truth — the full robotics-stack exercise.
